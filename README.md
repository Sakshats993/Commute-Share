# CommuteShare

CommuteShare is a community ride-sharing application for people travelling along similar routes. Drivers can publish rides and manage vehicles; passengers can search rides, request seats, and follow booking updates.

> **Project status:** Work in progress. The repository contains a locally runnable React and FastAPI application and automated tests. Docker Compose syntax is valid, but a container build/start has not been verified in the current environment. Production deployment, external OAuth, browser-based end-to-end coverage, and a full responsive visual review are not complete. Do not treat this project as production-ready.

## Features and limitations

The table describes the current implementation, not a production service guarantee.

| Area | Current implementation |
| --- | --- |
| Accounts | Password registration/login, Google and GitHub OAuth, JWT access tokens, profile editing, local avatar uploads, and role-based default avatars for passengers and drivers. |
| Vehicles and rides | Drivers can manage vehicles and rides. Passengers can search and filter rides. Route maps use Leaflet and public OpenStreetMap tiles; the displayed distance is straight-line only. |
| Bookings | Booking requests, driver confirmation, cancellation, full-ride waitlists, and promotion after a confirmed booking is cancelled are implemented. |
| Notifications and ratings | In-app notifications and ride-related ratings are implemented. |
| Boarding | The backend has signed QR-token generation and verification endpoints. A frontend QR scanning workflow was not found in the current source. |
| Payments | The application records payment status and offers admin status changes and payment history. It does not process, collect, or transfer money. |
| Safety | SOS events can be recorded, associated with an authorized active ride, and triaged by admins. The application does not contact emergency services or dispatch responders. |
| Administration and audit | Admin API/dashboard functions cover user, ride, booking, payment, and SOS management; audit records are created for selected operations. |

## Technology and architecture

- **Frontend:** React, Vite, React Router, Axios, Tailwind CSS, Leaflet, and React Leaflet.
- **Backend:** Python 3.12, FastAPI, Pydantic, and SQLAlchemy 2.
- **Database:** PostgreSQL 16 in the provided Compose configuration; Alembic manages schema migrations.
- **Authentication:** Password hashing and signed JWT access tokens. The browser stores the access token in `localStorage` and sends it as a bearer token.
- **Tests:** Pytest for backend tests and Node's built-in test runner for frontend tests. Ruff is included for Python linting.
- **Local environment:** Docker Compose can run PostgreSQL, the API, and the Vite development server.

The browser calls FastAPI through the Axios client. FastAPI routers validate requests with Pydantic schemas, use authentication dependencies, and delegate data operations to service modules. Services use SQLAlchemy sessions and PostgreSQL models. Alembic migrations define database changes. The API's interactive documentation is generated by FastAPI at `/docs` and `/redoc`.

See [Architecture](docs/ARCHITECTURE.md) for the request path and [Database schema](docs/DATABASE_SCHEMA.md) for the model overview.

## Prerequisites

For the documented local setup, use Python 3.12, Node.js 22 with npm, and Docker Compose with access to Docker Hub for the public base images. Alternatively, provide a local PostgreSQL 16 database. The repository's CI workflow uses Python 3.12 and Node.js 22. Frontend install/build commands run from `frontend/`; the root `package.json` is not used by Compose or CI.

## Run with Docker Compose

The Compose file is configured for local development. It binds PostgreSQL, the API, and Vite to loopback addresses. It uses `backend/.env.example` as the backend container's environment file; that file contains development-only credentials and a placeholder JWT secret. Do not reuse them outside a local development setup.

From the repository root:

```sh
docker compose up --build
```

After the services start, apply migrations in a second terminal:

```sh
docker compose exec backend alembic upgrade head
```

Open the frontend at <http://localhost:5173>, the API at <http://localhost:8000>, and interactive API docs at <http://localhost:8000/docs>. The API's `/health` endpoint reports that the process is responding; it does not check database connectivity.

Stop the services while keeping the PostgreSQL volume:

```sh
docker compose down
```

The named `postgres_data` volume persists database contents between starts. Avoid removing volumes unless you intentionally want to erase local data.

## Run services separately

These instructions run the API and frontend on the host and use the Compose PostgreSQL service. If PostgreSQL is already installed locally, use its host, port, database, and credentials instead.

1. Start only PostgreSQL from the repository root:

   ```sh
   docker compose up -d postgres
   ```

2. Create the backend environment file and edit it for a host process. The example URL uses the Compose DNS name `postgres`; change that hostname to `localhost` for a host-run API. Replace the example JWT secret with a generated local value.

   ```powershell
   Copy-Item backend/.env.example backend/.env
   python -c "import secrets; print(secrets.token_urlsafe(48))"
   ```

   Paste the generated value into `SECRET_KEY` in `backend/.env`. This file is ignored by Git. Keep it private.

3. Install backend dependencies and run migrations. In a new terminal:

   ```sh
   cd backend
   python -m venv .venv
   ```

   Activate the environment (`.venv\Scripts\Activate.ps1` in PowerShell, or `source .venv/bin/activate` in a POSIX shell), then:

   ```sh
   python -m pip install -r requirements.txt
   python -m alembic upgrade head
   python -m uvicorn main:app --reload --host 127.0.0.1 --port 8000
   ```

4. In another terminal, install and start the frontend:

   ```sh
   cd frontend
   npm ci
   npm run dev
   ```

Vite serves the app on port 5173 by default. The frontend API client defaults to `http://127.0.0.1:8000`.

## Configuration

The backend reads environment variables and a `.env` file from its current working directory. `backend/.env.example` is the Compose development configuration; it is not a production secret store.

| Variable | Purpose | Notes |
| --- | --- | --- |
| `DATABASE_URL` | SQLAlchemy and Alembic database connection | Required. Use `postgres` as the host inside Compose and `localhost` for a host-run API using the Compose database. |
| `SECRET_KEY` | Signs JWTs | Required. The checked-in example is a placeholder and must not be used for a deployed system. |
| `DEBUG` | Enables SQLAlchemy SQL echo | Defaults to `True`; use `False` outside local development. |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | Access-token lifetime | Defaults to 30 minutes; the example sets 60. |
| `ALGORITHM` | JWT signing algorithm | Defaults to `HS256`. |
| `BACKEND_CORS_ORIGINS` | Allowed browser origins | Defaults to `http://localhost:5173`; provide the exact frontend origin for another local port. |
| `LOG_LEVEL` | Declared in settings and the sample file | The current logger is fixed at `INFO`; changing this variable does not currently change the logger level. |

The backend settings class declares additional server, password, upload, and ride fields; see [config.py](backend/app/core/config.py) for their defaults and check the code references before relying on a setting. `APP_NAME`, `APP_VERSION`, `ENVIRONMENT`, `HOST`, `PORT`, `BCRYPT_ROUNDS`, `DEFAULT_SEARCH_RADIUS_KM`, `MAX_ACTIVE_RIDES_PER_DRIVER`, and `DEFAULT_ADMIN_EMAIL` are currently declared but are not read by application behavior. `API_V1_PREFIX` and the `MAP_DEFAULT_*` entries in the sample environment file are not currently consumed by the application settings or map component.

Optional frontend variables are `VITE_API_BASE_URL` (API origin) and `VITE_OSM_TILE_URL` (Leaflet tile URL). Vite embeds `VITE_*` values in the browser bundle; do not put secrets in them. The map defaults to `https://tile.openstreetmap.org/{z}/{x}/{y}.png`.

## Database migrations

Run migration commands from `backend/` after setting `DATABASE_URL`:

```sh
python -m alembic current
python -m alembic heads
python -m alembic upgrade head
```

Create a migration for a reviewed model change with:

```sh
python -m alembic revision --autogenerate -m "describe the change"
```

Review generated migration files before applying them. Do not run migrations against production or a database containing important data without a reviewed backup and an approved change plan.

## Authentication and roles

Registration accepts `driver` or `passenger`; it does not permit public registration as an administrator. Login returns a signed access token. Protected API requests send it as `Authorization: Bearer <token>`. Backend dependencies enforce active-user and role checks; frontend route guards are only a navigation aid. There is no refresh-token endpoint or Google/GitHub OAuth flow in the current routes.

See [Security notes](docs/SECURITY.md) for credential, upload, and deployment considerations.

## Security notes

- Never commit `.env` files, production credentials, user uploads, or database dumps. Use a generated secret and unique database credentials outside local development.
- The example Compose setup is for local development only. It uses `DEBUG=True`, an example JWT secret, and simple development database credentials.
- JWTs are stored by the frontend in `localStorage`; protect the application against cross-site scripting and use HTTPS in any deployment.
- Avatar files are stored on the backend filesystem. A multi-instance deployment would need an explicitly designed shared storage strategy; none is configured here.
- Configure TLS, production secrets, database backups, monitoring, and network policy before any deployment. No AWS deployment or production infrastructure is defined by this repository.
- SOS creates an in-app record and admin notifications; it does not call emergency services.
- For vulnerability reports, use a private channel with the repository maintainer. No security contact address is configured in this repository.

## Troubleshooting

| Symptom | Check |
| --- | --- |
| API cannot connect to PostgreSQL in Compose | Confirm the database is healthy and that `DATABASE_URL` uses host `postgres`, not `localhost`, inside the backend container. |
| Host-run API cannot resolve `postgres` | Change the host-run `backend/.env` URL to use `localhost`; `postgres` is the Compose service DNS name. |
| Frontend reports network or CORS errors | Confirm the API is on port 8000, Vite is on 5173, `VITE_API_BASE_URL` is correct, and `BACKEND_CORS_ORIGINS` includes the browser origin. |
| API starts but database routes fail | Apply migrations with `alembic upgrade head`; startup does not run migrations automatically. |
| A port is already in use | Stop the conflicting local process or adjust the Compose port mapping and matching frontend/CORS settings. |
| Docker build cannot pull base images | Check Docker daemon access and Docker Hub availability/rate limits. No Docker image build is performed by `docker compose config`. |

# 🌍 About the Project

CommuteShare is a **full-stack community-driven ride-sharing platform** designed around a simple idea:

> **If people are already travelling in the same direction, technology should make it easier for them to travel together.**

The platform allows users to discover rides, create rides, manage vehicles, book seats, join waitlists, rate other users, receive notifications, and access safety features.

What started as a ride-sharing application grew into a much larger full-stack system involving:

* Authentication
* Role-Based Access Control
* Database design
* Ride lifecycle management
* Booking workflows
* Waitlist promotion
* Reputation systems
* Notifications
* SOS events
* Admin dashboards
* Audit logging
* Payment tracking
* QR-based boarding logic
* Dockerized deployment
* Automated testing

CommuteShare was built with the goal of creating a project that behaves like a **real application**, not just a collection of CRUD APIs.

# ❗ The Problem

Daily commuting has several common problems:

🚗 Many vehicles travel with unused seats.

💰 Individual transportation can be unnecessarily expensive.

🌍 More vehicles contribute to congestion and environmental impact.

🤝 Finding trustworthy people travelling in similar directions is difficult.

📅 Coordinating rides manually through chats is inefficient.

🔒 Safety and accountability are important concerns in ride-sharing.

A real ride-sharing platform therefore needs more than just "create ride" and "book ride" buttons.

It needs systems for:

* Identity
* Trust
* Ride lifecycle management
* Booking conflicts
* Capacity management
* Waitlists
* Notifications
* Safety
* Reputation
* Administrative oversight

**CommuteShare was built around solving these engineering problems.**

# 🧠 Core Engineering Highlights

This project was intentionally structured beyond a basic CRUD application.

## Separation of Concerns

The backend follows a layered design:

```text
Route
  ↓
Schema
  ↓
Service
  ↓
Model
  ↓
Database
```

Each layer has a focused responsibility:

| Layer      | Responsibility               |
| ---------- | ---------------------------- |
| API Routes | HTTP requests and responses  |
| Schemas    | Validation and serialization |
| Services   | Business logic               |
| Models     | Database representation      |
| Database   | Persistent storage           |

```bash
git clone https://github.com/Sakshats993/Commute-Share.git
cd Commute-Share
```

---

## 2️⃣ Backend Setup

Navigate to the backend:

```bash
cd backend
```

Create a virtual environment:

### Windows

```bash
python -m venv venv
venv\Scripts\activate
```

### Linux / macOS

```bash
python -m venv venv
source venv/bin/activate
```

Install dependencies:

```bash
pip install -r requirements.txt
```

Create your environment configuration:

```bash
cp .env.example .env
```

Configure your environment variables.

Example:

```env
APP_NAME=CommuteShare
APP_VERSION=1.0.0
DEBUG=True

DATABASE_URL=postgresql+psycopg://postgres:your_password@localhost:5432/commuteshare

SECRET_KEY=CHANGE_THIS_TO_A_LONG_RANDOM_SECRET_KEY
ALGORITHM=HS256
ACCESS_TOKEN_EXPIRE_MINUTES=60

BACKEND_CORS_ORIGINS=["http://localhost:5173"]
```

Run migrations:

```bash
alembic upgrade head
```

Start the backend:

```bash
uvicorn main:app --reload
```

Backend:

```text
http://localhost:8000
```

Swagger Documentation:

```text
http://localhost:8000/docs
```
